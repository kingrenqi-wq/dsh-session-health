# 设计取舍

这份文档记录几个不显然的决定，方便后来改代码的人知道哪些是刻意的。

## 只读，不做动作

插件只读 `~/.dsh/sessions/**/session.v4.jsonl.zstd`，不写文件、不联网，也不停止、重试、压缩或发送任何东西。

原因：日志能证明的事情有限。"它走歪了"是一个判断，不是一个事实。把判断做成动作，误判一次就会打断用户正在做的事；做成读数，误判的代价只是多看一眼。

## 只报能指向证据的提示

一条提示必须能展开成"哪个工具、哪类错误、几条记录、哪些目标、哪一段 seq"。做不到这一点的信号（比如"感觉变慢了"）不显示。

## 失败要结构化

只认 `tool/result.data.error`；shell 工具另外认结尾的 `[exit code: N]`。正文里出现 `Error:`、代码示例、错误日志都不算失败。

原因：正文是任意文本，用它判断失败必然误报；而真实失败在日志里带结构化的 `{ name, code }`。

## 阈值从哪来

- 连续失败 2 次：再低会把正常的"换个路径再试"当成异常。
- 任务 300 秒：低于这个数，长任务还在正常范围内。
- 上下文 50% / 65%：自动压缩多数在 65–70% 之间发生，65% 以上往往已经看不到原始数值了。
- 提示保留 10 分钟：覆盖"人离开一下再回来"的常见时长。

这些都是**观察值**，不是统计结论。换模型、换窗口、换压缩策略都可能让它偏移。

## 数据完整性优先于可用性

帧解析分三态（完整 / 未写完 / 损坏）；遇到损坏或顺序异常时，宁可把读数标成"不可用"，也不沿用旧值。文件被替换或改写时，靠 inode 加已读前缀的哈希判断并重建缓存。

## 已知未验证

宿主重启、系统时钟跳变、多窗口、请求超时合并、提示分页这五项没有可靠验证过。见 README 的「已知限制」。
